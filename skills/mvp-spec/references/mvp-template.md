# MVP 요건 템플릿

`§0-2` 조건(진행 차단 항목이 2개 이상 비었을 때)에 해당할 때 사용자에게 제공하는 골격이다. 4개 항목만 담고 그 외는 넣지
않는다 — PRD 전체가 아니라 **게이트 통과에 필요한 최소 요건**이다.

사용자가 직접 채우거나, PM 계열 스킬·PRD 템플릿으로 작성한 내용을 이 구조에 옮긴다. 사용자가
**질의 보완 모드**(`references/fill-mode.md`)를 고르면 질문의 답을 이 구조에 채워 초안을 만든다.

---

## 제공 방식

파일로 만들어 제공한다. 안내 문구에 항목 이름만 나열하지 않는다 — 채울 자리가 있는 편이 훨씬
빨리 작성된다.

파일명은 `Master.md` 또는 `{서비스명}_Master.md`를 권한다. 여러 화면에 걸리는 규칙(공통 규칙 절)도 이 문서에 모으는 편이 관리가 쉽다.

## 템플릿 본문

````markdown

# {서비스명} — Master

## 1. 제공할 핵심 서비스와 주 이용자

어떤 서비스를 누구에게 제공하는가. **기능을 나열하지 않고** 한 문단으로 쓴다.
기능 없이 설명할 수 없다면 아직 범위를 정할 단계가 아니다.

> 예: 퇴근 후 운동하는 30대 직장인이 동네 운동 모임을 1분 안에 찾고 신청하는 앱.
> 지금은 오픈채팅·커뮤니티를 일일이 뒤져야 한다.

## 2. 포지셔닝과 유저 저니

**포지셔닝** — 다른 방법 대비 무엇이 다른가. 한 문장으로 쓴다.

> 예: 오픈채팅은 모임이 흩어져 있다. 우리는 내 동네 모임만 모아 보여준다.

**유저 저니** — 핵심 시나리오 2~3개. 화면 이름이 아니라 **행동 순서**로 쓴다.
메뉴 구성은 여기서 파생되므로 이것이 3번보다 먼저다.

```
시나리오 A: 진입 → 행동 → 행동 → 목적 달성
시나리오 B: ...
```

## 3. 메뉴 구성

2번 저니에서 도출한다. 저니 없이 정한 메뉴는 근거가 없다.
앱이면 화면 아래·위에 늘 보이는 메뉴(GNB), 웹이면 상단 메뉴다.
기존 서비스에 기능을 더하는 문서라면 "기존 메뉴 그대로"라고 한 줄 쓰면 된다.

```
Index
├ {대메뉴 1}
│  ├ {서브메뉴}
│  └ {서브메뉴}
├ {대메뉴 2}
└ ...

메뉴 밖 공통: Member(로그인·계정) · Etc(설정·전체메뉴)  ※ 결제가 있으면 Payment
```
````
