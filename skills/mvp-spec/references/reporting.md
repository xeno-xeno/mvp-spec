# 작업 리포팅 형식

`§0-R`·`§7`에서 리포팅할 때 참조한다. **기본 형식을 항상 쓰고, 상세 형식은 사용자가 요청할 때만
쓴다.** 기본 출력은 한 화면 분량이다.

---

## 기본 형식 (항상)

### 게이트 리포트 — 세 줄

```
유형: enhancement(고도화) · 출처 work_type
8개 중 점검 3 — 충족 1 문제정의(Master) · 7 우선순위(Briefing) / 미충족 5 유저저니 / 생략 5개
→ 진행 불가: 5 유저저니 없음 (전이 표 작성 불가)
```

| 줄 | 내용 |
|---|---|
| 1 | 작업 유형과 출처 (`work_type` / 본문 0번 / 서술 판단 / 사용자 답변) |
| 2 | 전체 8개 대비 점검·충족·미충족·생략. 충족 항목은 근거 파일명을 괄호로 |
| 3 | `→ 진행` / `→ 진행 가능(품질 저하: 항목명)` / `→ 진행 불가: 항목명 (불가능해지는 것 한 구절)` |

탭 단위 입력으로 게이트를 건너뛴 경우: `게이트 생략 — 탭 단위 입력`

미충족이 있으면 리포트 바로 아래에 질문한다. 최대 2개, 한 줄 + 선택지, 기본값 표시.

### 작업 리포트 — 네 덩어리

```
| 화면 ID               | 레벨 | MVP | 상태 수 |
| Feed-Latest-List-01   | Main | 1   | 3       |
| Feed-Article-01       | Detail | 1 | 2       |
1순위 2장 · 상태 합계 5장 = 화면 설계 상한

찾은 문제 2건
· 결제 화면 정의 0개 → Payment 영역 신규 정의, 상태 3행 추가
· 알림 목록 진입점·정의가 문서 분리 → 기능형으로 재분류

남은 판단 1건
· [미결] 필터 전이 방식 (바텀시트 가정)

✓ 완료 — 갱신본 Feed_updated.md · 다음: 화면 설계로 인계 가능
```

| 규칙 | 내용 |
|---|---|
| 마지막 줄 | 항상 완료 선언. 미결이 있어도 완료로 선언한다 |
| 찾은 문제 | 발견 → 처리를 **한 줄에**. 최대 5줄, 초과는 "외 n건" |
| 남은 판단 | 최대 3줄, 초과는 "외 n건" |
| 핵심 한 줄 | 화면 수·범위를 바꾼 발견이 있으면 `핵심: …` 한 문장 (선택) |
| 넣지 않는 것 | 없던 것→추가 표, 애프터 발췌, 설명 문단 |

## 상세 형식 (요청 시)

사용자가 "자세히", "상세 리포트", "비포/애프터 보여줘"라고 요청할 때만 쓴다. 순서대로 작성한다.

## §0-R 게이트 리포팅

### 1) 작업 유형과 점검 범위

**전체 항목 수와 점검 대상 수를 함께 밝힌다.** 번호만 나열하면 사용자가 전체 규모를 모른다.

```
작업 유형: enhancement (고도화)   출처: 프론트매터 work_type
전체 8개 항목 중 3개 점검 · 5개 생략

점검: 1 문제정의 · 5 유저저니 · 7 기능우선순위
생략: 2 타겟유저 · 3 포지셔닝 · 4 수익모델 · 6 GNB구성 · 8 성공지표
```

출처를 함께 적는다 — `프론트매터` / `본문 0번` / `문서 서술 판단` / `사용자 답변` 중 하나.

### 2) 판정 결과

**8개 항목을 전부 표에 올린다.** 생략 항목도 빼지 않는다 — 무엇이 점검되지 않았는지가
사용자에게 필요한 정보다.

```
| # | 항목        | 판정 | 근거 위치                  |
| 1 | 문제 정의    | ✓    | Master.md §서비스 개요     |
| 2 | 타겟 유저    | 생략 | (고도화)                   |
| 5 | 유저 저니    | ✗    | —                          |
| 7 | 기능 우선순위 | ✓    | Briefing.md §개발 우선순위 |
  ... (8개 전부)

충족 2  ·  미충족 1  ·  생략 5
```

충족 항목은 **근거 위치를 반드시 적는다** — 위치를 못 적으면 충족이 아니다. 마지막에
**충족·미충족·생략 개수를 합산한다.**

### 3) 게이트 통과 여부

```
진행 불가 — 5 유저 저니 미충족
            (진행을 막는 항목 4·5·6·7 중 1개)
```

4·5·6·7 중 미충족이 있으면 `진행 불가`, 그 외 필수만 미충족이면 `진행 가능(품질 저하 예상)`,
전부 충족이면 `진행`이다. 어느 쪽이든 **해당 항목명을 함께 적는다.**

### 4) 미충족 항목의 영향

**무엇이 불가능해지는지** 구체적으로 적는다. "유저 저니가 없습니다"만으로는 사용자가 중요도를
판단할 수 없다.

```
예: 유저 저니 미정의 → 각 화면의 전이 목적지를 도출할 근거가 없음.
    §1 전이 표를 채울 수 없어 화면 장수 계산이 불가능하다.
```

### 5) 선행 작업 제안

진행을 막는 항목(4·5·6·7)을 채우기 위한 질문을 제시한다. 우선순위 순으로 2~3개.

## §7 작업 리포팅

### 1) 화면 목록 확정 결과

```
| 화면 ID | 레벨 | MVP | 상태 수 |
```

마지막에 **"MVP 1순위 N장, 상태 수 합계 M장이 화면 설계 상한"**을 명시한다. 이 숫자가
다음 단계(화면 설계)의 입력이 된다.

### 2) 없던 것 → 추가

형식 적용으로 새로 생긴 것. 비포에 무엇이 없었는지 구체적으로 적는다.

```
| 구분      | 비포                | 애프터              |
| 상태 분기 | 0건                 | 화면당 3행          |
| 전이 방식 | 목적지만            | 이동/모달/시트 명시 |
```

### 3) 검증 루프에서 찾은 것 → 반영

§3에서 발견한 미싱링크·공백을 **어떻게 처리했는지**까지 적는다. 발견만 나열하면 사용자가
반영 여부를 알 수 없다.

```
| # | 발견                          | 애프터 처리                    |
| 1 | 무료 회원 알림 화면 미정의    | 상태 표에 `무료` 행 추가       |
```

### 4) 애프터 구조 발췌

갱신된 문서의 화면 섹션 하나를 코드블록으로 보여준다. 전문이 아니라 **대표 1개**만.

### 5) 가장 큰 변화

**판단에 영향을 주는 발견 하나를 문단으로 설명한다.** 표만 나열하면 무엇이 중요한지 묻힌다.

**무엇을 발견했는지가 아니라, 그 발견이 다음 단계에서 무엇을 바꾸는지**를 적는다. 화면 수,
상태 비교 방식, 우선순위 범위처럼 후속 작업량에 직결되는 결론으로 연결한다.
