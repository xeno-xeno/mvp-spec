# 게이트 판정 근거

`§0-2` 유형별 점검 항목을 정할 때, 또는 유형 판정이 애매할 때 읽는다.

---

## 유형 확인 질문 문구

판정이 애매할 때 한 줄로 묻는다. 정의는 사용자가 물을 때만 설명한다.

```
"작업 유형? 신규(new) / 고도화(enhancement) / 리뉴얼(renewal)"
```

정의: 신규 — 서비스 자체를 새로 정의 · 고도화 — 기존 서비스에 기능·화면 추가 · 리뉴얼 — 기존 서비스의
구조를 다시 짬.

---

## 유형 판정 신호

| 신호 | 유형 |
|---|---|
| Master 문서에 GNB·수익모델이 확정 서술 | 고도화 |
| "기존 A 서비스에 B 기능 추가" 식 서술 | 고도화 |
| 서비스명이 가칭이거나 포지셔닝을 논하는 중 | 신규 |
| "3.0 리뉴얼", "구조 개편" 같은 표현 | 리뉴얼 |

애매하면 묻는다. 추측으로 정하면 게이트 전체가 어긋난다.

---

**고도화에서 1·5·7만 점검하는 이유**

| 항목 | 고도화에서도 필요한 이유 |
|---|---|
| 문제 정의 | 추가하려는 기능이 어떤 문제를 푸는지 모르면 화면을 정할 수 없다 |
| 유저 저니 | 기존 서비스의 어디에 붙는지, 진입·이탈 경로가 무엇인지는 매번 새로 정의된다 |
| 기능 우선순위 | 추가 기능 중 무엇을 이번 범위에 넣을지는 항상 판단이 필요하다 |

수익모델·GNB·포지셔닝은 상위 문서에 이미 있으므로 다시 점검하지 않는다. **만약 상위 문서에도
없다면 그건 고도화가 아니므로** §0-1로 돌아가 유형을 다시 판정한다.

**리뉴얼을 신규와 같게 보는 이유**

구조를 다시 짜면 GNB·저니가 바뀌고, 그러면 화면 ID 체계도 전부 영향받는다. 포지셔닝이 유지되는
경우라도 근거 위치는 확인해야 하므로 필수로 둔다.

**IA·GNB는 유저 저니에서 파생된다.** 유저 플로우의 주 목적이 정보 구조를 구축하는 것이므로,
6번이 5번 없이 먼저 정해졌다면 그 자체가 검토 대상이다 — 저니 없이 정한 메뉴 구성은 근거가 없다.


---

## Master 승격 판단

`#done` 처리 전에 **화면을 넘나드는 규칙**은 Master로 옮긴다. 옮기지 않으면 기준이 사라진다.

판단 기준: **한 화면에만 적용되면 주석에, 여러 화면에 걸리면 Master에.**

예: 조건 판정 임계값, 강조 기준값, 마스킹 표현 방식, 데이터 보관 기간, 용어 사전.

이들은 여러 화면에 공통 적용되므로, 탭 문서에 남겨두면 그 문서를 닫은 뒤 기준이 사라진다.

## 자주 걸리는 패턴

전부 형식은 갖췄는데 내용이 어긋난 경우다. 체크리스트로는 잡히지 않는다.

| 패턴 | 유형 |
|---|---|
| 결제·로그인이 MVP 1순위인데 화면 정의 0개 | 구조 미싱링크 |
| 화면 정의와 진입점이 서로 다른 문서에 흩어짐 | 동선 단절 |
| 같은 기능의 권한이 IA와 탭 문서에서 다름 | BM 일관성 |
| 복사·붙여넣기로 동일 블록이 중복 | 문서 품질 |
| 우선순위 1 항목의 콘텐츠가 "미정"으로만 표기 | 정의 공백 |

## 문서 수명 운영 상세

탭별 MVP 문서는 **화면 설계를 위한 입력**이다. 생성이 끝나면 역할이 끝나고,
이후 정본은 화면 설계 산출물이다.

```
Master · IA          지속 유지          #live
탭별 MVP 문서         화면 설계까지만     #draft → #ready → #done
화면 설계 산출물      생성 이후 정본
```

| 태그 | 의미 |
|---|---|
| `#draft` | 작성 중 |
| `#ready` | 형식 4덩어리 완료. 화면 설계 대기 |
| `#done` | 생성 완료. **갱신하지 않음** |
| `#live` | 지속 유지 (Master · IA) |

프론트매터에 생성된 화면 ID를 남긴다 — 문서 ↔ 화면 설계 연결이 이 한 줄로 해결된다.

```yaml
tags: [done]
spec_format: 1
screens: Feed-Latest-List-01, Feed-Article-01, Explore-ItemDetail-01
completed: YYYY-MM-DD
```

### Master로 승격할 것

`#done` 처리 전에 **여러 화면에 걸리는 규칙**은 Master로 옮긴다. 판단 기준과 예시는
`references/gate-rationale.md` 참조.

## 판정 깊이 예시

러프하게라도 서술돼 있으면 충족이다. 애매하면 충족 + `(파일·러프)`.

| 문서에 있는 것 | 판정 |
|---|---|
| "무료는 목록까지, 유료는 상세 분석" | **충족** — 경계가 있다 |
| "수익화 방안 검토 중" | 미충족 — 경계가 없다 |
| "탐색 → 항목 선택 → 상세" | **충족** — 순서가 있다 |
| "사용자가 원하는 것을 찾는다" | 미충족 — 순서가 없다 |

## 선행 작업 질의 범위

| 게이트 단계에서 묻는 것 | 묻지 않는 것 (§2·§3의 몫) |
|---|---|
| 무료/유료 경계의 기준 | 어느 화면의 어느 요소를 가릴지 |
| 핵심 플로우 2~3개의 순서 | 각 단계의 화면 구성 |
| GNB 후보 영역 | 서브탭 구성·화면 장수 |
| 1순위 기능 목록 | 각 기능의 상태 분기 |
