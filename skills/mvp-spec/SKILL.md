# MVP 문서 정리 & 기획 검토

MVP 문서를 **화면 설계로 넘길 수 있는 상태**로 만드는 스킬. 형식을 맞추는 것과 내용을 검토하는 것,
두 가지를 한다.

산출물은 **정리된 MVP 문서 + 확정된 화면 목록**이다. 실제 화면 설계(와이어프레임·스토리보드)
작성은 이 스킬의 범위 밖이며, 확정된 목록을 다음 단계로 넘긴다.

## 적용 순서

두 단계로 나뉜다. **1단계를 통과하지 못하면 2단계로 넘어가지 않는다.**

```
[1단계] MVP 요건 게이트
  §0-1 작업 유형 분기 (신규 / 고도화 / 리뉴얼)
        ↓
  §0-2 유형별 필수 항목 점검  →  §0-R 게이트 리포팅  →  미충족 시 §0-3 템플릿(선택: 질의 보완) · 선행 작업
                                    ↓ 통과
[2단계] 문서 정리 + 화면 목록 확정
  §1 형식 적용  →  §2 질의  →  §3 기획 검토  →  §6 산출물  →  §7 작업 리포팅
                                    ↓
                          화면 설계 단계로 인계
```

리포팅이 두 번 나온다. **§0-R은 "작업을 시작할 수 있는가"**, **§7은 "무엇이 바뀌었는가"**를
답한다. **게이트가 `→ 진행`이면 멈추지 않고 같은 응답에서 2단계로 이어간다** — 게이트 3줄은
§7 최종 리포트 맨 위에 붙인다. 미충족이나 질문이 있을 때만 멈춘다.

**탭 단위로 끊는다.** 2단계는 전체 문서를 한 번에 다루지 않는다. 탭 하나면 화면 3~6개,
확인 질문 1~2개다. 단 1단계 게이트는 **문서 세트 전체에 한 번만** 수행한다 — 포지셔닝·수익모델은
탭별로 다르지 않다.

## 실행 원칙 — 가정하지 말고 검증한다

Andrej Karpathy가 지적한 LLM 에이전트의 반복 실수 패턴을 문서 검토 맥락으로 옮겼다
(`karpathy-guidelines` 스킬로도 공개돼 있으나, **함께 설치할 필요는 없다**).

| | 원칙 | 이 검토에서 |
|---|---|---|
| 1 | 가정하지 말라 | 해석이 여러 개면 모두 제시한다. 조용히 하나를 고르지 않는다 |
| 2 | 최소한만 만들라 | 요청하지 않은 항목·절차를 문서에 추가하지 않는다 |
| 3 | 건드린 것만 고치라 | 절 번호 재정렬 시 참조 링크가 깨지는지 확인한다 |
| 4 | 검증 루프 | §3의 6단계를 끝까지 돌린다. 수정 후 **옛 값이 남아있는지 반대 방향으로 재검색**한다 |

## 커뮤니케이션 원칙 — 짧게 말한다

사용자에게 보이는 모든 텍스트에 적용한다. 이 스킬은 판단을 돕는 도구이지 설명하는 도구가 아니다.

| 원칙 | 내용 |
|---|---|
| 결론 먼저 | 첫 줄에 결과나 요청을 쓴다. 인사·서론·"~하겠습니다" 예고·맺음 요약을 쓰지 않는다 |
| 질문은 짧게 | 한 번에 **최대 2개**. 한 줄 + 선택지로 쓰고 **기본값을 표시**한다(열린 질문은 예시). 질문 앞에 이유를 설명하지 않는다 |
| 확실한 것은 묻지 않는다 | "~로 진행합니다" 한 줄로 알리고 넘어간다 |
| 중간 보고 없음 | "지금 점검 중입니다" 같은 진행 서술을 하지 않는다. 질문이 필요할 때와 최종 리포트만 낸다 |
| 같은 말을 두 번 하지 않는다 | 표에 있는 내용을 문장으로 다시 풀지 않는다 |
| 상세는 요청 시 | 기본 리포트는 **한 화면 분량**이다. 근거·비포/애프터·전체 표는 사용자가 요청할 때 `references/reporting.md`의 상세 형식으로 낸다 |

사용자가 **"기본으로", "그대로"**라고 답하면 표시된 기본값으로 진행한다. 이유는 사용자가 "왜?"라고
물을 때만 설명한다.

## §0. MVP 요건 게이트

화면 설계로 넘어가기 전 **문서가 갖춰야 할 최소 요건**을 점검한다.

### 입력 범위를 먼저 확인한다

게이트는 **문서 세트 전체**를 대상으로 한다. 탭 문서 하나만 받았다면 상위 문서(Master·IA)가
없어 2·3·4·6·8이 전부 미충족으로 나오는데, 그건 문서가 부실한 게 아니라 **입력이 부족한 것**이다.

| 받은 입력 | 처리 |
|---|---|
| Master(또는 상위 전략 문서) 포함 | 정상 진행 |
| **탭 문서만** | 상위 문서를 요청한다. 없으면 게이트를 건너뛰고 §1로 진행 |

```
"{파일명}은 탭 문서입니다. 상위 문서(Master·IA)가 있으면 함께 올려 주세요.
 없으면 이 문서 범위로 진행합니다. (기본: 진행)"
```

**상위 문서가 없다고 작업을 막지 않는다.** 게이트의 목적은 품질 확인이지 관문 통과가 아니다.
건너뛴 경우 §0-R에 `게이트 생략 — 탭 단위 입력`으로 표기하고 §1로 간다. 이후 단계는 **탭 문서
안의 정보로 대신한다** — 대메뉴는 탭 이름, 무료 행 유형은 탭 문서의 권한 서술, 우선순위는 탭 문서의
MVP 표기. 근거가 없는 칸은 비워 두지 말고 `[미결] 상위 근거 없음`으로 적는다.

게이트는 문서 세트당 **한 번만** 수행하고, 탭별 작업마다 반복하지 않는다.

항목 구성은 공개된 MVP 체크리스트·PRD 템플릿이 공통으로 요구하는 요소(문제 정의, 타겟 페르소나,
가치 제안, 유저 플로우, 우선순위 기능 목록, 수익 검증, 성공 지표)에 화면 ID 부여에 필요한
**GNB·메뉴 구성**을 더한 것이다. 유형 판정·항목 선택의 상세 근거는
`references/gate-rationale.md`에 있다.

### §0-1. 작업 유형 분기 — 먼저 확인한다

**점검 전에 작업 유형을 확정한다.** 유형에 따라 필수 항목이 달라진다. 이걸 건너뛰면 고도화
프로젝트에 신규 서비스용 질문이 나가서 "이미 다 있는데 왜 묻느냐"가 된다.

확인 순서: ① 프론트매터 `work_type` (`new` / `renewal` / `enhancement`) → ② 본문 0번 절
→ ③ 문서 서술에서 판단 → ④ 애매하면 묻는다.

①②가 있으면 그대로 쓴다 — 템플릿으로 작성된 문서는 이 필드를 갖고 있어 묻지 않고 분기된다.

③의 판단 근거: Master에 GNB·수익모델이 확정 서술돼 있으면 고도화, 서비스명이 가칭이거나
포지셔닝을 논하는 중이면 신규, "리뉴얼·구조 개편" 표현이 있으면 리뉴얼이다.

④ **추측으로 유형을 정하지 않는다** — 게이트 전체가 어긋난다. 세 유형의 정의를 제시하고 묻는다
(문구 예시는 `references/gate-rationale.md`).

확정된 유형은 §0-R 리포트 1줄에 출처와 함께 명시하고, 문서에 `work_type`이 없었다면 **갱신본
프론트매터에 추가한다** — 다음 호출 때 다시 묻지 않게 된다.

### §0-2. 유형별 점검 항목

| # | 항목 | 신규 | 고도화 | 리뉴얼 |
|---|---|---|---|---|
| 1 | **문제 정의** | 필수 | 필수 | 필수 |
| 2 | **타겟 유저 / 페르소나** | 필수 | 생략 | 필수 |
| 3 | **가치 제안 / 포지셔닝** | 필수 | 생략 | 필수 |
| 4 | **수익모델** | 필수 | 생략 | 필수 |
| 5 | **유저 저니 / 주요 플로우** | 필수 | 필수 | 필수 |
| 6 | **GNB · 주요 메뉴 구성** | 필수 | 생략 | 필수 |
| 7 | **기능 우선순위** | 필수 | 필수 | 필수 |
| 8 | 성공 지표 | 선택 | 생략 | 선택 |

| 표기 | 의미 |
|---|---|
| **필수** | 점검한다. 미충족이면 보고한다 |
| **선택** | 점검한다. 없어도 진행한다 |
| **생략** | 점검하지 않는다 |

**생략 항목을 충족으로 적지 않는다.** 점검하지 않은 것을 충족으로 적으면 나중에 그 항목이
실제로 없다는 게 드러났을 때 근거를 추적할 수 없다.

### 진행을 막는 항목 — 4 · 5 · 6 · 7

필수 항목 중 **수익모델 · 유저 저니 · GNB 구성 · 기능 우선순위**는 미충족 시 §1로 넘어가지
않는다. 각각 마스킹 판정 · 전이 표 · 화면 ID 레벨 · 화면 장수 계산의 직접 입력이라, 없으면
작업 자체가 불가능하다.

1·2·3·8은 미충족이어도 진행한다. 문서 품질에 영향을 주지만 화면 목록 도출을 막지 않는다.
고도화에서는 4·6이 생략 대상이므로 **실제로 진행을 막는 것은 5·7뿐**이다.

### 점검 방법

```
① 작업 유형을 확정한다 (§0-1)        → verify: 신규 / 고도화 / 리뉴얼 중 하나로 정해졌는가
② 유형에 해당하는 항목만 점검한다 (§0-2). 생략 항목은 건너뛴다
③ 각 항목을 문서 세트 전체에서 찾는다
   → verify: 근거 위치(파일명 + 절)를 지목할 수 있는가
④ 근거를 지목할 수 없으면 미충족으로 판정한다
⑤ 점검 대상인 4·5·6·7 중 하나라도 미충족이면 §0-R 보고 후 §0-3·선행 작업으로 진입
```

### 판정 깊이 — 존재 확인이지 완성도 심사가 아니다

**항목이 러프하게라도 서술돼 있으면 충족이다.** 게이트는 "이 항목이 정의됐는가"를 보는 것이고,
"충분히 상세한가"를 보는 것이 아니다. 상세화는 §1~§3에서, 그것도 화면 단위로 한다.

판정 예시는 `references/gate-rationale.md` 참조.

애매하면 **충족으로 판정하고 리포트 2줄에 `(파일·러프)`로 표기한다.** 미충족으로 몰면 질의가 폭발하고,
사용자가 이미 아는 것을 다시 설명하게 된다.

### §0-3. 문서가 부족하면 템플릿을 제공한다

**기본은 템플릿이다.** `references/mvp-template.md`를 파일로 제공하고 부족한 절을 짚어준다.
이때 **질의 보완 모드**(질문으로 함께 채우기)를 선택지로 함께 주고, 사용자가 고를 때만 켠다.
완성형 PRD를 대신 써 주는 기능이 아니라, 게이트 항목을 러프한 수준까지 채우는 기능이다.

판정 기준은 **이번 유형에서 점검 대상인 진행 차단 항목**이다 — 신규·리뉴얼은 4·5·6·7(4개),
고도화는 5·7(2개). 유형을 먼저 확정해야(§0-1) 이 판정이 성립한다.

| 점검 대상 차단 항목 중 미충족 | 처리 |
|---|---|
| **전부** | 템플릿 제공 + **중단**. 문서 부재로 간주 |
| **2개 이상, 전부는 아님** | 템플릿 제공 + 질문 병행. 중단하지 않음 |
| **1개** | 질문만 |
| 1·2·3만 미충족 | 템플릿 없음. 리포트에 보고만 |

**전부 미충족 (중단)** — 템플릿을 첨부하고 두 줄로 끝낸다.

```
"{미충족 항목}이 모두 없어 검토를 시작할 수 없습니다. 템플릿을 첨부했습니다.
 채워 오시겠어요, 질문으로 함께 채울까요? (기본: 템플릿)"
```

**일부 미충족 (계속 진행)** — 템플릿을 첨부하고 바로 질문한다. 질문만으로 채우면 왕복이 길어지고
사용자가 답을 어디에 적을지 모르기 때문이다.

```
"미정의: 5 유저 저니 · 6 GNB · 7 우선순위. 템플릿의 해당 절을 채워 주세요.
 먼저 확인:
 1. 핵심 시나리오 2~3개의 순서는?
 2. 상시 접근이 필요한 영역은? (GNB 후보)
 나머지도 질문으로 채울 수 있습니다. (기본: 템플릿)"
```

### 질의 보완 모드 (선택)

사용자가 고른 경우에만 켠다. 절차와 질문 예는 `references/fill-mode.md`.

| 규칙 | 내용 |
|---|---|
| 범위 | 유형별 필수 항목 중 **문서에 없는 것만** (신규·리뉴얼 1~7, 고도화 1·5·7). 8은 묻지 않는다 |
| 순서 | 템플릿 작성 순서 — 1·2 → 3·4 → 5 → 6 → 7 |
| 깊이 | 게이트를 통과할 러프한 수준까지. 화면 구성·카피는 묻지 않는다 |
| 형식 | 한 번에 최대 2개, 앞에 진행도 `(3/7)`. 열린 질문은 기본값 대신 예시 |
| 모를 때 | `[미결]`로 두고 넘어간다. 원하면 앞의 답에서 후보 2~3개를 제안 — **확정은 사용자** |
| 6 GNB | 묻지 않고 5의 플로우에서 도출해 제안 → 확인 |
| 결과 | 템플릿 구조로 채운 Master 초안 파일 + 게이트 3줄. 통과하면 "2단계로 이어갈까요? (기본: 예)" |

### 선행 작업 — 질문으로 끌어낸다

미충족 항목을 **임의로 만들지 않는다.** 사용자에게 물어 답을 받아 문서에 반영한다.

**질의는 러프한 수준에서 끊는다.** 게이트를 통과할 만큼만 받고, 상세는 §1~§3에서 화면 단위로
다룬다. 화면 하나하나의 구성·카피·조건을 이 단계에서 묻지 않는다.

묻는 것은 경계 기준·플로우 순서·GNB 후보·1순위 목록까지다. 화면 구성·가릴 요소·상태 분기는
§2·§3의 몫이라 여기서 묻지 않는다 (범위 표는 `references/gate-rationale.md`).

```
"1. 수익 방식? (구독 / 인앱결제 / 광고 / 미정)
 2. 무료·유료 경계 기준?"
```

질문은 **4·5·6·7 우선**, 한 번에 최대 2개. 이유를 앞에 붙이지 않는다.

답변을 받으면 해당 항목을 Master 문서(또는 새 문서)에 반영하고, 게이트를 재점검한다.

## §0-R. 게이트 리포팅

§0 점검 결과를 보고한다. 미충족·질문이 있으면 여기서 멈추고, `→ 진행`이면 멈추지 않는다.

**세 줄**로 보고한다. 상세 형식(8행 표·미충족 영향)은 요청 시
`references/reporting.md`에서 낸다.

```
유형: enhancement(고도화) · 출처 work_type
8개 중 점검 3 — 충족 1 문제정의(Master) · 7 우선순위(Briefing) / 미충족 5 유저저니 / 생략 5개
→ 진행 불가: 5 유저저니 없음 (전이 표 작성 불가)
```

- 2줄에 **전체 8개 대비 점검·충족·미충족·생략**을 모두 담는다
- 충족 항목은 근거 파일명을 괄호로 적는다 — 적을 수 없으면 충족이 아니다. 근거가 러프하면 `(파일·러프)`
- 3줄은 `→ 진행` / `→ 진행 가능(품질 저하: 항목명)` / `→ 진행 불가: 항목명 (불가능해지는 것 한 구절)`
- 미충족이 있으면 바로 질문한다 (최대 2개)

게이트를 건너뛴 경우(탭 단위 입력)는 `게이트 생략 — 탭 단위 입력`으로 표기하고 §1로 간다.

## §1. 문서 형식

탭 문서의 **화면 단위 섹션**에 네 덩어리를 붙인다. 기존 내용은 그대로 두고 추가만 한다.

```
H2  화면명
    > IA 참조줄 (경로 | MVP 순위 | 권한)
H3  상태     — 기본 / 빈상태 / 무료 3행. 무료 행에 유형 표기
H3  전이     — 트리거 / 목적지 / 방식
H3  주석     — 번호 목록
```

작성 예시는 `references/doc-format.md` 참조.

### 각 덩어리의 제약

| 덩어리 | 제약 | 어기면 |
|---|---|---|
| IA 참조줄 | 값 복사가 아닌 참조 표시. 다르면 IA가 맞음 | 사일런트 드리프트 |
| 상태 | **기본 / 빈상태 / 무료** 3행. 무료 행은 **유형 필수**(아래) | 데이터가 다 있는 화면만 그려짐 |
| 전이 | 방식(이동 / 모달 / 시트) 필수 | 장수가 달라짐 |
| 주석 | **번호 목록.** 산문 금지 | 화면 설계 문서로 옮길 수 없음 |

**주석 줄 길이** 한 줄 38자 이내 권장(한글 기준, 좁은 설명 패널에 옮겨지므로). 넘으면 수동 개행하고 다음 줄을 5칸 들여쓴다.

주석 블록은 화면 설계 문서의 설명 영역에 그대로 옮겨진다. 산문으로 쓰면 옮길 수 없으므로 이
형식이 자동화의 전제다.

### 무료 행 유형

수익모델(게이트 4)이 정한 무료/유료 경계를 **화면 단위로 옮기는 칸**이다. 유형이 없으면 화면
설계에서 무엇을 그리고 무엇을 주석으로 뺄지 정할 수 없다.

| 유형 | 의미 | 무료 행 예 |
|---|---|---|
| `동일` | 무료·유료 차이 없음. 유료 구분이 없는 서비스·화면 포함 | `동일` |
| `마스킹` | 같은 화면에서 일부만 가림 | `마스킹 — 신호 라벨 · 흐림+🔒` |
| `분기` | 무료면 다른 화면으로 전환 | `분기 → Feed-Promo-01` |
| `차단` | 진입 자체를 막고 안내·결제로 보냄 | `차단 → 구독 안내(바텀시트)` |

- `마스킹`은 **대상 요소와 표현**을 함께 적는다. "마스킹됨"만으로는 재현할 수 없다
- `분기`의 목적지 화면은 화면 목록에도 있어야 한다 (§3 검증 2단계에서 확인)

### 화면 ID

**이 스킬이 가(假)ID를 부여한다.** 화면 목록을 확정하면서 붙이고, 전이 표·검증·프론트매터가 이
ID를 쓴다. 화면 설계 단계에서 확정되면 IA에 역으로 채운다. 확정 전에는 바뀔 수 있지만 폐기된
번호는 재사용하지 않는다.

표기는 영문, 기술 순서(대메뉴 → 소메뉴 → 화면)를 따르며 압축하지 않는다 — `FEED-ART-01`처럼
줄이면 어떤 타입의 본문인지 구분이 안 된다. 상세 규칙(레벨 4종, GNB 밖 대메뉴, 한 화면 = 한 ID)은
`references/screen-id.md` 참조.

## §2. 질의 프로세스

문서를 읽고 화면 목록을 확정하는 절차. **확실한 것은 묻지 않는다.**

### 화면 후보 도출

| 신호 | 예 |
|---|---|
| 서브탭 | 탭 A / B / C |
| 별도 문서로 분리된 영역 | 콘텐츠 본문 구조 |
| 권한이 다른 동일 기능 | 무료 프로모션 / 유료 전체 |
| 모달·시트로 명시된 것 | 요약 모달 |
| 단계가 서술된 것 | 대시보드 → 항목 선택 → 리스트 |

### 질문 규칙

- **최대 2개.** 그 이상이면 문서가 부족한 것이므로 문서를 먼저 보완한다
- 확실한 화면은 목록에 넣고 **알리기만** 한다
- 질문은 "몇 장으로 볼 것인가"에만 한정한다. 디자인·카피는 묻지 않는다

```
화면 5개 확정. 확인 2건:
1. 서브탭 A·B — 별도 페이지 / 탭 전환 1장? (기본: 별도)
2. 콘텐츠 본문 — 타입별 2장으로 진행? (기본: 예)
```

### 탭 밖 화면 수집

어느 탭에도 속하지 않는 화면은 그때그때 별도 목록에 모은다. 탭을 다 돌고 나서 `Common`
문서로 정리한다.

```
흔한 예: login / payment / 헤더 영역(알림·프로필·계정·구독상태·설정)
→ IA 시트 하단에 라벨로만 존재. MVP 1순위인데 화면 수 0
```

이들은 특정 대메뉴에 속하지 않아 탭별 문서를 아무리 자세히 써도 계속 빠진다.

## §3. 기획 검토 — 검증 루프로 돌린다

§4 체크리스트가 **형식 검증**(빈 칸이 있는가)이라면, 이 절은 **내용 검토**(이게 맞는가)다.
형식은 갖췄는데 내용이 비었거나 어긋난 경우는 체크리스트로 잡히지 않는다.

"MVP 문서 검토해"는 약한 목표다 — 눈에 띈 것만 지적하고 끝난다. 아래처럼 성공 기준을
명시하면 우연에 의존하지 않는다.

### 검증 루프

결과는 §7의 "찾은 문제"로만 보고한다. **단계별 결과를 나열하지 않는다.**

```
1. 우선순위 1 항목 전체 열거        → verify: 각 항목의 화면 수가 0이 아닌가
   (IA가 없으면 Master의 7 기능 우선순위로 대신한다)
2. 모든 전이 목적지 수집             → verify: 실재하는 화면 ID인가
3. 모든 화면의 진입 경로 확인        → verify: 빈 칸이 없는가 (고아 화면)
4. 모든 화면의 이탈 경로 확인        → verify: 나갈 길이 있는가 (막다른 화면)
5. IA·탭문서·수익화문서 권한 대조    → verify: 값이 충돌하지 않는가
6. 우선순위 1 항목의 정의 상태 확인  → verify: "미정"·"별도 논의"가 없는가
```

### 검토 항목

**타겟·목적 정합성** — 각 화면이 Master의 사용자 질문에 대응하는가. 대응하는 질문이 없는
화면은 존재 이유를 재검토한다.

**구조 미싱링크** — 우선순위 1인데 화면 수가 0인 항목. 정의와 진입점이 서로 다른 문서에
흩어진 화면. 어느 대메뉴에도 속하지 않는 화면.

**동선 흐름** — 고아 화면(진입 경로 없음), 막다른 화면(나갈 길 없음, 빈 상태 포함),
미정의 목적지(전이가 실재하지 않는 ID를 가리킴), 진입 경로 과다.

**BM 일관성** — 권한 정의가 IA ↔ 탭 문서 ↔ 수익화 문서 사이에 충돌하지 않는가. 무료/유료
경계가 전환 설계와 맞는가 — 가치는 보여주고 접근만 막는 구조인지.

**정의 공백** — 우선순위 1에 "미정"·"별도 논의" 상태 항목이 있는가. 카피가 예시 수준인
채로 확정 표기됐는가.

### 자주 걸리는 패턴

형식은 갖췄는데 내용이 어긋난 경우들 — 결제·로그인이 1순위인데 화면 0개, 화면 정의와 진입점이
다른 문서에 흩어짐, 같은 기능의 권한이 IA와 탭 문서에서 다름, 복붙으로 블록 중복, 1순위 항목이
"미정"으로만 표기. 상세는 `references/gate-rationale.md` 참조.

- [ ] 무료 회원이 볼 화면이 정의돼 있는가

- [ ] 주석이 번호 목록인가 (산문 아님)
- [ ] 탭 밖 화면이 Common 목록에 들어갔는가

## §5. 문서 수명 — 태그로 관리

탭별 MVP 문서는 **화면 설계로 넘기기 위한 입력**이다. 화면 설계가 끝나면 정본은 그 산출물로
넘어가고, 문서는 폐기하지 않고 `#done`으로 남긴다 — "왜 이렇게 정했나"가 사라지지 않게.

태그는 `#draft`(작성 중) → `#ready`(형식 4덩어리 완료) → `#done`(갱신하지 않음), Master·IA는
`#live`(지속 유지)다. 프론트매터의 `screens`로 문서 ↔ 화면 설계를 연결한다. 태그 운영 상세와
Master 승격 판단은 `references/gate-rationale.md` 참조.

## §6. 산출물 — 문서를 실제로 갱신한다

**검토만 하고 끝내지 않는다.** 원본 MVP 문서에 §1 형식을 적용한 갱신본을 만들어 제공한다.

```
1. 원본 문서를 읽는다
2. §2 질의로 화면 목록 확정 · §3 검증 루프로 미싱링크 탐색
3. 화면 단위 섹션에 네 덩어리(참조줄·상태·전이·주석)를 추가한다
4. 검증 루프에서 찾은 것을 해당 섹션에 반영한다
5. 프론트매터에 `spec_format`·`work_type`·태그·`screens`(화면 ID)를 넣는다
6. 파일로 저장해 제공  → verify: 사용자가 받을 수 있는 상태인가
```

원본을 덮어쓰지 않는다. 같은 파일명으로 새로 만들어 제공하고, 사용자가 원래 위치에서 교체한다.

## §7. 작업 리포팅 — 한 화면 분량

갱신본을 제공할 때 아래 **네 덩어리**만 낸다. 비포/애프터 상세는 요청할 때만 낸다
(`references/reporting.md`).

```
| 화면 ID | 레벨 | MVP | 상태 수 |
  ...
1순위 N장 · 상태 합계 M장 = 화면 설계 상한

찾은 문제 k건
· 발견 → 처리
· 발견 → 처리                  (최대 5줄, 초과는 "외 n건")

남은 판단 j건
· [미결] ...                   (최대 3줄, 초과는 "외 n건")

✓ 완료 — 갱신본 {파일명} · 다음: 화면 설계로 인계 가능
```

- **마지막 줄은 항상 완료 선언**이다. 미결이 남아 있어도 완료로 선언한다 — 이 스킬의 범위는 끝났고
  남은 것은 다음 단계나 사용자 판단의 몫이다
- "찾은 문제"는 **발견과 처리를 한 줄에** 쓴다. 발견만 나열하지 않는다
- 화면 수나 범위를 바꾼 핵심 발견이 있으면 문제 목록 아래 `핵심: …` 한 문장을 더할 수 있다
- 기본 출력에 넣지 않는 것: 없던 것→추가 표, 애프터 발췌, 설명 문단

## 인계 — 화면 설계 단계로

화면 목록이 확정되면 다음 단계로 넘긴다. 넘기는 형식은 **출력 계약**
`references/handoff-format.md`(`spec_format: 1`)이다 — 화면 목록 표, 화면별 상태·전이 표와 주석,
무료 행 유형, `[미결]`. 하위 단계(사람이든 도구든)는 이 계약만 전제로 읽는다.

형식을 바꿀 때는 계약 파일의 버전 규칙을 따른다. 바꾸면 하위 도구가 깨질 수 있다.
