# MVP 문서 정리 & 기획 검토

MVP 문서를 **화면 설계로 넘길 수 있는 상태**로 만드는 스킬. 형식을 맞추는 것과 내용을 검토하는 것,
두 가지를 한다.

산출물은 **정리된 MVP 문서 + 확정된 화면 목록**이다. 실제 화면 설계(와이어프레임·스토리보드)
작성은 이 스킬의 범위 밖이며, 확정된 목록을 다음 단계로 넘긴다.

## 적용 순서

두 단계로 나뉜다. **1단계를 통과하지 못하면 2단계로 넘어가지 않는다.**

```
[1단계] MVP 요건 게이트
  §0-1 필수 항목 점검  →  §0-R 게이트 리포팅  →  미충족 시 §0-2 질문·템플릿 · 선행 작업
                                    ↓ 통과
[2단계] 문서 정리 + 화면 목록 확정
  §1 형식 적용  →  §2 질의  →  §3 기획 검토  →  §6 산출물  →  §7 작업 리포팅
                                    ↓
                          화면 설계 단계로 인계
```

리포팅이 두 번 나온다. **§0-R은 "작업을 시작할 수 있는가"**, **§7은 "무엇이 바뀌었는가"**를
답한다. **게이트가 `→ 진행`·`→ 진행 가능`이면 멈추지 않고 같은 응답에서 2단계로 이어간다** — 게이트 2줄은
§7 최종 리포트 맨 위에 붙인다(질문으로 한 번 멈췄다면 게이트 2줄은 첫 응답에만 쓰고 최종 리포트에서는 반복하지 않는다). 필수 항목(2·3·4)이 미충족이거나 질문이 있을 때만 멈춘다.

**탭 단위로 끊는다.** 2단계는 전체 문서를 한 번에 다루지 않는다. 탭 하나면 화면 3~6개,
확인 질문 1~2개다. 단 1단계 게이트는 **문서 세트 전체에 한 번만** 수행한다 — 서비스 정의·저니는
탭별로 다르지 않다.

## 실행 원칙 — 가정하지 말고 검증한다

Andrej Karpathy가 지적한 LLM 에이전트의 반복 실수 패턴을 문서 검토 맥락으로 옮겼다
(`karpathy-guidelines` 스킬로도 공개돼 있으나, **함께 설치할 필요는 없다**).

| | 원칙 | 이 검토에서 |
|---|---|---|
| 1 | 가정하지 말라 | 해석이 여러 개면 모두 제시한다. 조용히 하나를 고르지 않는다 |
| 2 | 최소한만 만들라 | 요청하지 않은 항목·절차를 문서에 추가하지 않는다 |
| 3 | 건드린 것만 고치라 | 절 번호 재정렬 시 참조 링크가 깨지는지 확인한다 |
| 4 | 검증 루프 | §3의 5단계를 끝까지 돌린다. 수정 후 **옛 값이 남아있는지 반대 방향으로 재검색**한다 |

## 커뮤니케이션 원칙 — 짧게 말한다

사용자에게 보이는 모든 텍스트에 적용한다. 이 스킬은 판단을 돕는 도구이지 설명하는 도구가 아니다.

| 원칙 | 내용 |
|---|---|
| 결론 먼저 | 첫 줄에 결과나 요청을 쓴다. 인사·서론·"~하겠습니다" 예고·맺음 요약을 쓰지 않는다 |
| 질문은 짧게 | 한 번에 **최대 2개**. 한 줄 + 선택지로 쓰고 **기본값을 표시**한다(열린 질문은 예시). 질문 앞에 이유를 설명하지 않는다 |
| 확실한 것은 묻지 않는다 | "~로 진행합니다" 한 줄로 알리고 넘어간다 |
| 중간 보고 없음 | "지금 점검 중입니다" 같은 진행 서술을 하지 않는다. 질문이 필요할 때와 최종 리포트만 낸다 |
| 같은 말을 두 번 하지 않는다 | 표에 있는 내용을 문장으로 다시 풀지 않는다 |
| 상세는 요청 시 | 기본 리포트는 **한 화면 분량**이다. 근거·비포/애프터·전체 표는 사용자가 요청할 때 `references/reporting.md`의 상세 형식으로 낸다 |

사용자가 **"기본으로", "그대로"**라고 답하면 표시된 기본값으로 진행한다. 이유는 사용자가 "왜?"라고
물을 때만 설명한다.

## §0. MVP 요건 게이트

화면 설계로 넘어가기 전 **문서가 갖춰야 할 최소 요건**을 점검한다.

### 입력 범위를 먼저 확인한다

게이트는 **문서 세트 전체**를 대상으로 한다. 탭 문서 하나만 받았다면 상위 문서(Master·IA)가
없어 1·2·3이 미충족으로 나오는데, 그건 문서가 부실한 게 아니라 **입력이 부족한 것**이다.

| 받은 입력 | 처리 |
|---|---|
| Master(또는 상위 전략 문서) 포함 | 정상 진행 |
| **탭 문서만** (Master·IA 없이 한 대메뉴만 다루는 문서) | 탭 문서의 `상위 문서: [[...]]` 링크가 같은 폴더에 있으면 그 파일을 먼저 읽고, 없을 때만 상위 문서를 요청한다. 끝내 없으면 점검을 건너뛰고 §1로 진행 |
| Master가 `관련 문서`·`[[링크]]`로 다른 파일을 가리킴 | 비어 있는 점검 항목(우선순위·메뉴 등)을 찾는 데 필요한 링크만 같은 폴더에서 읽는다. 탭 문서는 2단계에서 처리한다. 폴더에 없으면 리포트에 적고 멈추지 않고 진행한다 |

```
"{파일명}은 탭 문서입니다. 상위 문서(Master·IA)가 있으면 함께 올려 주세요.
 없으면 이 문서 범위로 진행합니다. (기본: 진행)"
```

상위 문서를 같은 폴더에서 찾지 못한 탭 문서만 받았으면 위 문구로 묻고 **멈춘다**. 사용자가 "기본으로"라고 답하거나 상위 문서가 없다고 하면 진행한다.

**상위 문서가 없다고 작업을 막지 않는다.** 게이트의 목적은 품질 확인이지 관문 통과가 아니다.
건너뛴 경우 §0-R에 `점검 생략 — 탭 문서만 받음`으로 표기하고 §1로 간다. 이후 단계는 **탭 문서
안의 정보로 대신한다** — 대메뉴는 탭 이름, 우선순위는 탭 문서의 MVP 표기.
근거가 없는 칸은 비워 두지 말고 `[미결] 상위 근거 없음`으로 적는다.

게이트는 문서 세트당 **한 번만** 수행하고, 탭별 작업마다 반복하지 않는다.

항목 구성은 공개된 MVP 체크리스트·PRD 템플릿이 공통으로 요구하는 요소(문제·타겟, 가치 제안, 유저 플로우,
우선순위 기능 목록)를 일반 사용자 눈높이로 3개로 묶고, 화면 ID 부여에 필요한 **메뉴 구성**을 더해 4개로 만든 것이다.
수익모델·성공 지표는 화면 설계의 입력이 아니라 뺐다. 항목 선택의 상세 근거는
`references/gate-rationale.md`에 있다.

### §0-1. 점검 항목

초기 서비스 기획용이라 작업 유형을 나누지 않는다. 항목은 4개다.

| # | 항목 | 진행 |
|---|---|---|
| 1 | **제공할 핵심 서비스와 주 이용자** | 점검 — 미충족이어도 진행 |
| 2 | **포지셔닝과 유저 저니** | **필수** |
| 3 | **메뉴 구성** (화면 아래·위에 늘 보이는 메뉴) | **필수** |
| 4 | **기능 우선순위** | **필수** |

- 2번은 **유저 저니가 있으면 충족**이다. 포지셔닝이 없으면 리포트 1줄에 `(저니만)`으로 표기한다
- 기존 서비스에 기능을 더하는 문서라면 3번은 "기존 메뉴 그대로"라고 한 줄 적혀 있으면 충족이다. 그런 문서로 읽히는데 메뉴 서술이 없으면 "기존 메뉴 그대로 진행할까요? (기본: 예)"로 묻는다. 대메뉴 이름이 문서에 없으면 이름도 함께 묻는다(화면 ID의 앞부분이 된다)
- 3번은 있는데 2번 저니가 없으면 3번은 충족으로 두되 리포트 1줄에 `(저니 없이 정한 메뉴)`로 표기한다. 메뉴는 저니에서 파생되므로 근거가 없다는 경고다
- 표기 예: `충족 4 서비스·이용자(대화) · 저니(Master·저니만) · 메뉴(Master) · 우선순위(Master) / 미충족 없음`. 첨부 없이 대화로 받은 내용은 `(대화)`로 적는다

### 진행을 막는 항목 — 2 · 3 · 4

**유저 저니(2) · 메뉴 구성(3) · 기능 우선순위(4)**는 미충족 시 §1로 넘어가지 않는다. 각각 화면 이동 정리 ·
화면 ID 대메뉴 · 화면 장수 계산의 직접 입력이라, 없으면 작업 자체가 불가능하다.

1번은 미충족이어도 진행한다. 문서 품질에 영향을 주지만 화면 목록 도출을 막지 않는다.

### 점검 방법

```
① 4개 항목을 문서 세트 전체에서 찾는다
   → verify: 근거 위치(파일명 + 절, 대화로 받은 것은 `(대화)`)를 지목할 수 있는가
② 근거를 지목할 수 없으면 미충족으로 판정한다
③ 2·3·4 중 하나라도 미충족이면 §0-R 보고 후 §0-2·선행 작업으로 진입
```

### 판정 깊이 — 존재 확인이지 완성도 심사가 아니다

**항목이 러프하게라도 서술돼 있으면 충족이다.** 게이트는 "이 항목이 정의됐는가"를 보는 것이고,
"충분히 상세한가"를 보는 것이 아니다. 상세화는 §1~§3에서, 그것도 화면 단위로 한다.

판정 예시는 `references/gate-rationale.md` 참조.

애매하면 **충족으로 판정하고 리포트에 `(파일·러프)`로 표기한다.** 미충족으로 몰면 질의가 폭발하고,
사용자가 이미 아는 것을 다시 설명하게 된다.

### §0-2. 문서가 부족하면 질문 또는 템플릿으로 채운다

`references/mvp-template.md`를 파일로 제공하고 부족한 절을 짚어준다(차단 항목이 2개 이상 비었을 때). **질의 보완 모드**(질문으로 함께 채우기)는
필수 3개가 모두 없을 때 **기본**이고, 그 외에는 사용자가 고를 때만 켠다.
완성형 PRD를 대신 써 주는 기능이 아니라, 게이트 항목을 러프한 수준까지 채우는 기능이다.

판정 기준은 **진행 차단 항목 2·3·4** 중 미충족 개수다.

| 차단 항목 중 미충족 | 처리 |
|---|---|
| **3개 전부** | 템플릿 첨부 + 질문으로 시작할지 묻고 **중단**. 기본은 질문 |
| **2개** | 템플릿 제공 + 질문 병행. 모드 선택은 묻지 않고 바로 질문하고 답을 기다린다 |
| **1개** | 질문만 하고 답을 기다린다 |
| 1번만 미충족 | 템플릿·질문 없음. 리포트에 적고 **멈추지 않고 진행** |

**전부 미충족 (중단)** — 템플릿을 첨부하고 두 줄로 끝낸다. 사용자가 "기본으로"·"질문으로"라고 답하면 `references/fill-mode.md`대로 바로 질문을 시작한다.

```
"유저 저니 · 메뉴 구성 · 기능 우선순위가 모두 없어 검토를 시작할 수 없습니다. 템플릿을 첨부했습니다.
 질문으로 함께 채울까요, 템플릿을 채워 오시겠어요? (기본: 질문)"
```

**2개 미충족** — 템플릿을 첨부하고 모드 선택 없이 바로 질문한다. 질문만으로 채우면 왕복이 길어지고
사용자가 답을 어디에 적을지 모르기 때문이다.

```
"미정의: 2 유저 저니 · 3 메뉴 구성. 템플릿의 해당 절을 채워 주세요.
 먼저 확인:
 1. 핵심 시나리오 2~3개의 순서는?
 2. 상시 접근이 필요한 영역은? (메뉴 후보)
 나머지도 질문으로 채울 수 있습니다. (기본: 템플릿)"
```

### 질의 보완 모드 (선택)

필수 3개가 모두 없으면 기본으로 켜고, 그 외에는 사용자가 고른 경우에만 켠다. 절차와 질문 예는 `references/fill-mode.md`.

| 규칙 | 내용 |
|---|---|
| 범위 | 점검 항목 중 **문서에 없는 것만** (1~4). 2번은 저니가 없을 때만 묻는다 |
| 순서 | 템플릿 작성 순서 — 1 → 2 → 3 → 4 |
| 깊이 | 게이트를 통과할 러프한 수준까지. 화면 구성·카피는 묻지 않는다 |
| 형식 | 한 번에 최대 2개, 앞에 진행도 `(3/N)` — N은 이번에 실제로 묻는 질문 수. 열린 질문은 기본값 대신 예시 |
| 모를 때 | `[미결]`로 두고 넘어간다. 원하면 앞의 답에서 후보 2~3개를 제안 — **확정은 사용자** |
| 3 메뉴 구성 | 묻지 않고 2의 저니에서 도출해 제안 → 확인 |
| 결과 | 템플릿 구조로 채운 Master 초안 파일 + 게이트 2줄. 통과하면 "2단계로 이어갈까요? (기본: 예)" |

### 선행 작업 — 질문으로 끌어낸다

미충족 항목을 **임의로 만들지 않는다.** 사용자에게 물어 답을 받아 문서에 반영한다.

**질의는 러프한 수준에서 끊는다.** 게이트를 통과할 만큼만 받고, 상세는 §1~§3에서 화면 단위로
다룬다. 화면 하나하나의 구성·카피·조건을 이 단계에서 묻지 않는다.

묻는 것은 서비스 한 줄·핵심 시나리오 순서·메뉴 후보·1순위 목록까지다. 화면 구성·상태 분기는
§2·§3의 몫이라 여기서 묻지 않는다 (범위 표는 `references/gate-rationale.md`).

```
"1. 핵심 시나리오 2~3개의 순서는?
 2. 상시 접근이 필요한 영역은? (메뉴 후보)"
```

질문은 **2·3·4 우선**(질의 보완 모드는 1→2→3→4 순서), 한 번에 최대 2개. 이유를 앞에 붙이지 않는다.

답변을 받으면 해당 항목을 Master 문서(또는 새 문서)에 반영하고, 게이트를 재점검한다.

---

## §0-R. 게이트 리포팅

§0 점검 결과를 보고한다. 필수 항목(2·3·4)이 미충족이면 여기서 멈추고, `→ 진행`·`→ 진행 가능`이면 멈추지 않는다.

**두 줄**로 보고한다. 상세 형식(4행 표·미충족 영향)은 요청 시
`references/reporting.md`에서 낸다.

```
4개 중 충족 2 서비스·이용자(Master) · 4 우선순위(Briefing) / 미충족 2 유저저니 · 3 메뉴
→ 진행 불가: 2 유저저니 · 3 메뉴 없음 (화면 이동·화면 ID 정리 불가)
```

- 1줄에 **4개 중 충족·미충족**을 담는다
- 충족 항목은 근거 파일명을 괄호로 적는다(대화로 받은 것은 `(대화)`). 근거를 댈 수 없으면 충족이 아니다. 근거가 러프하면 `(파일·러프)`
- 2줄은 `→ 진행` / `→ 진행 가능(품질 저하: 항목명)` / `→ 진행 불가: 항목명 (불가능해지는 것 한 구절)`
- 필수 항목(2·3·4)이 미충족이면 바로 질문한다 (최대 2개). 1번만 미충족이면 묻지 않고 이어 진행한다

게이트를 건너뛴 경우(탭 단위 입력)는 `점검 생략 — 탭 문서만 받음`으로 표기하고 §1로 간다.

## §1. 문서 형식

탭 문서의 **화면 단위 섹션**에 네 덩어리를 붙인다. 기존 내용은 그대로 두고 추가만 한다.
원래 제목(`## CALL 탭` 등)은 바꾸지 않고, 화면 섹션(`## {화면 ID} — {화면명}`)을 관련 절 뒤에 새로 추가한다.

```
H2  {화면 ID} — {화면명}
    > IA 참조줄 (경로 | MVP 순위)
H3  상태     — 기본 / 빈상태 2행
H3  이동     — 트리거 / 목적지 / 방식
H3  주석     — 번호 목록
```

작성 예시는 `references/doc-format.md` 참조.

### 각 덩어리의 제약

| 덩어리 | 제약 | 어기면 |
|---|---|---|
| IA 참조줄 | 값 복사가 아닌 참조 표시. 다르면 IA가 맞음. IA가 없으면 메뉴 구성의 경로를 쓴다 | 사일런트 드리프트 |
| 상태 | **기본 / 빈상태** 2행 필수 | 데이터가 다 있는 화면만 그려짐 |
| 이동 | 목적지는 화면 ID(목록에 없으면 이름 + `※ 미정의`, 같은 화면이면 `같은 화면 내`·`뒤로`), 방식은 `화면 이동`·`모달`·`바텀시트`·`같은 화면 내`·`뒤로` 중 하나 필수 | 장수가 달라짐 |
| 주석 | **번호 목록.** 산문 금지 | 화면 설계 문서로 옮길 수 없음 |

**주석 줄 길이** 한 줄 38자 이내 권장(한글 기준, 좁은 설명 패널에 옮겨지므로). 넘으면 수동 개행하고 다음 줄을 5칸 들여쓴다.

주석 블록은 화면 설계 문서의 설명 영역에 그대로 옮겨진다. 산문으로 쓰면 옮길 수 없으므로 이
형식이 자동화의 전제다.

### 화면 ID

**이 스킬이 가(假)ID를 부여한다.** 화면 목록을 확정하면서 붙이고, 이동 표·검증·프론트매터가 이
ID를 쓴다. 화면 설계 단계에서 확정되면 IA에 역으로 채운다. 확정 전에는 바뀔 수 있지만 폐기된
번호는 재사용하지 않는다.

표기는 영문, 기술 순서(대메뉴 → 소메뉴 → 화면)를 따르며 압축하지 않는다 — `FEED-ART-01`처럼
줄이면 어떤 타입의 본문인지 구분이 안 된다. 상세 규칙(레벨 4종, 메뉴 밖 대메뉴, 한 화면 = 한 ID)은
`references/screen-id.md` 참조.

## §2. 질의 프로세스

문서를 읽고 화면 목록을 확정하는 절차. **확실한 것은 묻지 않는다.**

### 화면 후보 도출

| 신호 | 예 |
|---|---|
| 서브탭 | 탭 A / B / C |
| 별도 문서로 분리된 영역 | 콘텐츠 본문 구조 |
| 모달·시트로 명시된 것 | 요약 모달 |
| 단계가 서술된 것 | 대시보드 → 항목 선택 → 리스트 |

### 질문 규칙

- **최대 2개.** 그 이상이면 문서가 부족한 것이므로 문서를 먼저 보완한다
- 확실한 화면은 목록에 넣고 **알리기만** 한다
- 질문은 "몇 장으로 볼 것인가"에만 한정한다. 디자인·카피는 묻지 않는다

```
화면 5개 확정. 확인 2건:
1. 서브탭 A·B — 별도 페이지 / 탭 전환 1장? (기본: 별도)
2. 콘텐츠 본문 — 타입별 2장으로 진행? (기본: 예)
```

### 탭 밖 화면 수집

어느 탭에도 속하지 않는 화면은 그때그때 별도 목록에 모은다. 탭을 다 돌고 나서 `Common`
문서로 정리한다. `_Screens.md`를 쓰는 경우 Common은 그 파일의 마지막 절로 두고, 프론트매터 `screens`는 대메뉴를 돌 때마다 누적한다.

```
흔한 예: login / 헤더 영역(알림·프로필·계정·설정)
→ IA 시트 하단에 라벨로만 존재. MVP 1순위인데 화면 수 0
```

이들은 특정 대메뉴에 속하지 않아 탭별 문서를 아무리 자세히 써도 계속 빠진다.

모든 탭을 돌고 나면 **이동 도착지를 한 번 다시 맞춘다** — 처리 중 `※ 미정의`로 남긴 도착지를 확정된 화면 ID로 바꾸고, 끝까지 없는 것은 `이름 ※ 미정의`로 두고 남은 판단에 적는다. 바뀐 파일은 다시 제공하고 리포트에 한 줄 적는다.

## §3. 기획 검토 — 검증 루프로 돌린다

§4 체크리스트가 **형식 검증**(빈 칸이 있는가)이라면, 이 절은 **내용 검토**(이게 맞는가)다.
형식은 갖췄는데 내용이 비었거나 어긋난 경우는 체크리스트로 잡히지 않는다.

"MVP 문서 검토해"는 약한 목표다 — 눈에 띈 것만 지적하고 끝난다. 아래처럼 성공 기준을
명시하면 우연에 의존하지 않는다.

### 검증 루프

결과는 §7의 "찾은 문제"로만 보고한다. **단계별 결과를 나열하지 않는다.**

```
1. 이번 탭의 우선순위 1 항목 열거        → verify: 각 항목의 화면 수가 0이 아닌가
   (IA가 없으면 Master의 4 기능 우선순위로 대신한다)
   화면이 없는 기능(엔진·백엔드 등)은 제외하고 리포트에 한 줄만 적는다
2. 모든 이동 목적지 수집             → verify: 실재하는 화면 ID인가
3. 모든 화면의 진입 경로 확인        → verify: 빈 칸이 없는가 (고아 화면)
4. 모든 화면의 이탈 경로 확인        → verify: 나갈 길이 있는가 (막다른 화면)
5. 우선순위 1 항목의 정의 상태 확인  → verify: "미정"·"별도 논의"가 없는가
```

### 검토 항목

**타겟·목적 정합성** — 각 화면이 Master의 주 이용자가 하려는 일에 대응하는가. 대응하는 일이 없는
화면은 존재 이유를 재검토한다.

**구조 미싱링크** — 우선순위 1인데 화면 수가 0인 항목. 정의와 진입점이 서로 다른 문서에
흩어진 화면. 어느 대메뉴에도 속하지 않는 화면.

**동선 흐름** — 고아 화면(진입 경로 없음), 막다른 화면(나갈 길 없음, 빈 상태 포함),
미정의 목적지(이동의 목적지가 실재하지 않는 ID), 진입 경로 과다.

**정의 공백** — 우선순위 1에 "미정"·"별도 논의" 상태 항목이 있는가. 카피가 예시 수준인
채로 확정 표기됐는가.

### 자주 걸리는 패턴

형식은 갖췄는데 내용이 어긋난 경우들 — 로그인이 1순위인데 화면 0개, 화면 정의와 진입점이
다른 문서에 흩어짐, 복붙으로 블록 중복, 1순위 항목이 "미정"으로만 표기. 상세는
`references/gate-rationale.md` 참조.

## §4. 체크리스트

- [ ] 화면마다 빈 상태가 있는가
- [ ] 이동에 방식(화면 이동 / 모달 / 바텀시트 등)이 있는가
- [ ] 주석이 번호 목록인가 (산문 아님)
- [ ] 탭 밖 화면이 Common 목록에 들어갔는가 (모든 탭 처리 후)
- [ ] 문서 상단(제목 아래)에 화면 목록 표가 있는가
- [ ] 프론트매터에 `spec_format`·`screens`가 있는가

## §5. 문서 수명 — 태그로 관리

탭별 MVP 문서는 **화면 설계로 넘기기 위한 입력**이다. 화면 설계가 끝나면 정본은 그 산출물로
넘어가고, 문서는 폐기하지 않고 `#done`으로 남긴다 — "왜 이렇게 정했나"가 사라지지 않게.

태그는 `#draft`(작성 중) → `#ready`(형식 4덩어리 완료, `[미결]`이 남아도 됨) → `#done`(갱신하지 않음), Master·IA는
`#live`(지속 유지)다. 프론트매터의 `screens`로 문서 ↔ 화면 설계를 연결한다. 태그 운영 상세와
Master 승격 판단은 `references/gate-rationale.md` 참조.

## §6. 산출물 — 문서를 실제로 갱신한다

**검토만 하고 끝내지 않는다.** 원본 MVP 문서에 §1 형식을 적용한 갱신본을 만들어 제공한다.

```
1. 원본 문서를 읽는다
2. §2 질의로 화면 목록 확정 · §3 검증 루프로 미싱링크 탐색
3. H1 제목과 그 아래 인용줄 다음에 화면 목록 표를 넣는다 (`references/handoff-format.md` §2)
4. 화면 단위 섹션에 네 덩어리(참조줄·상태·이동·주석)를 추가한다
5. 검증 루프에서 찾은 것을 해당 섹션에 반영한다
6. 프론트매터에 `spec_format`·태그·`screens`(화면 ID)를 넣는다
7. 파일로 저장해 제공  → verify: 사용자가 받을 수 있는 상태인가
```

원본을 덮어쓰지 않는다. `{원본이름}_updated.md`로 새로 만들어 제공하고, 사용자가 원본과 교체한다.

탭 문서가 없고 Master(또는 질의로 만든 Master 초안)만 있으면, 메뉴 구성의 대메뉴별 섹션으로 정리한 `{서비스명}_Screens.md` 한 파일을 새로 만든다. 2단계는 대메뉴 하나씩 끊어서 돌린다.

## §7. 작업 리포팅 — 한 화면 분량

갱신본을 제공할 때 아래 **네 덩어리**만 낸다. 비포/애프터 상세는 요청할 때만 낸다
(`references/reporting.md`).

```
| 화면 ID | 레벨 | MVP | 상태 수 |
  ...
1순위 N장 · 상태 합계 M장 = 화면 설계 최대 장수

찾은 문제 k건
· 발견 → 처리
· 발견 → 처리                  (최대 5줄, 초과는 "외 n건")

남은 판단 j건
· [미결] ...                   (최대 3줄, 초과는 "외 n건")

✓ 완료 — 갱신본 {파일명} · 다음: 화면 설계로 인계 가능
```

- **마지막 줄은 항상 완료 선언**이다. 미결이 남아 있어도 완료로 선언한다 — 이 스킬의 범위는 끝났고
  남은 것은 다음 단계나 사용자 판단의 몫이다
- "찾은 문제"는 **발견과 처리를 한 줄에** 쓴다. 발견만 나열하지 않는다
- `N장·M장`은 MVP 1순위 화면만 센다. 2순위 이하는 화면 목록 표에는 올리되 이 숫자에서 뺀다
- 화면이 없는 기능(엔진 등)은 표 아래에 `(제외: …)` 한 줄로 적는다
- 화면 수나 범위를 바꾼 핵심 발견이 있으면 문제 목록 아래 `핵심: …` 한 문장을 더할 수 있다
- 기본 출력에 넣지 않는 것: 없던 것→추가 표, 애프터 발췌, 설명 문단

## 인계 — 화면 설계 단계로

화면 목록이 확정되면 다음 단계로 넘긴다. 넘기는 형식은 **출력 계약**
`references/handoff-format.md`(`spec_format: 2`)이다 — 화면 목록 표, 화면별 상태·이동 표와 주석,
`[미결]`. 하위 단계(사람이든 도구든)는 이 계약만 전제로 읽는다.

형식을 바꿀 때는 계약 파일의 버전 규칙을 따른다. 바꾸면 하위 도구가 깨질 수 있다.
